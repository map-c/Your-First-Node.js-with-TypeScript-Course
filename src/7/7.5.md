# 本章小结

本章从一个最小 Hono 服务开始，逐步补齐了现代 TypeScript Web API 的主要组成部分。

| 能力 | 对应实现 |
| --- | --- |
| 启动 HTTP 服务 | Hono 加 `@hono/node-server` |
| 路由和中间件 | `app.get()`、`app.post()` 和 `app.use()` |
| 输入和输出校验 | oRPC procedure 加 Zod schema |
| API 契约 | oRPC 生成 OpenAPI 3.1 文档 |
| 交互式文档 | Scalar API Reference |
| 完整全栈架构 | Cella 的 Hono、PostgreSQL、SDK 和 React 模块 |
| 运行状态观测 | Apitally Hono 中间件 |

## 必须掌握的要点

1. Hono 应用本身不会在 Node.js 中监听端口，需要 Node.js 适配器调用 `serve()`。
2. 中间件有执行顺序，日志、认证和监控中间件应在需要覆盖的路由之前注册。
3. API 输入不能只依赖 TypeScript 类型，运行时数据仍然需要 Zod 等工具校验。
4. OpenAPI 文档应从实际接口契约生成，避免手工文档与代码逐渐不一致。
5. 模板和框架不是同一个层级。Cella 提供完整应用结构，Hono 提供 Web 请求处理能力。
6. 接入监控后还要验证路由粒度、数据环境和敏感信息处理，不能只验证依赖安装成功。

## 练习

可以继续扩展本章的任务 API：

1. 增加 `GET /tasks/{id}`，任务不存在时返回 404。
2. 增加修改完成状态和删除任务的 procedure。
3. 把内存数组替换成 SQLite 或 PostgreSQL。
4. 为写操作增加认证中间件，并把用户信息放进 oRPC context。
5. 使用 Hono 的 `app.request()` 为成功、校验失败和 404 编写测试。
6. 接入监控后验证每个路由的状态码和响应时间。

## 完成检查

结束本章前，至少完成以下检查：

```bash
npm run build
curl -f http://localhost:3000/
curl -f http://localhost:3000/api/tasks
curl -f http://localhost:3000/api/openapi.json
curl -f http://localhost:3000/api/docs
```

还应确认无效任务输入返回 400、未知路由返回 404，并检查监控平台中是否出现预期的请求数据。

现在已经可以使用 TypeScript 和 Hono 搭建一个结构清晰、接口有契约、运行状态可观测的 Node.js Web 服务。后续可以继续学习数据库事务、认证授权、缓存、队列、OpenTelemetry 和部署策略。
